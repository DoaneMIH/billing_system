01

System Overview

The NOVALINK Billing System is a web-based application that manages everything an Internet Service Provider (ISP) needs to operate: subscriber records, monthly bill generation, payment collection, and financial reporting.

👥

Customer Management

Create, update, and track subscriber records. Manage connection status from pending installation through disconnection.

📄

Billing Generation

Auto-generate monthly bills for all active subscribers with automatic balance carryover from previous months.

💳

Payment Collection

Record payments from cashiers, generate official receipts (OR), and mark billing records as paid or partial.

📊

Financial Reports

Monthly billing, sales, unpaid accounts, disconnection risk, and last-payment-date reports. All printable.

🔐

Role-Based Access

Three roles control what each user can see and do: Admin, Accounting, and Cashier.

⚡

Real-Time Updates

AJAX polling every 5 seconds auto-refreshes dashboards and key pages when data changes, without full reload.

System Modules

Click each module to expand the full explanation.

🔐 Authentication — login.php, logout.php, config.php ▶

Login via username + password using PHP's password_verify() against the bcrypt hash stored in the users table. On success, a session is created with user_id, role, and full_name. Every protected page calls check_permission() at the very top — if the user isn't logged in or lacks the required role, they're immediately redirected. Logout destroys the session completely.

Key helpers in config.php: getDBConnection() · check_permission($role) · log_activity() · sanitize_input() · format_currency()

📊 Dashboard — index.php ▶

Shows 4 real-time stat cards: Total Subscribers, Active Subscribers, Unpaid Bills, and Monthly Revenue. Uses SQL COUNT() and SUM() aggregation queries. Quick Action buttons link to the most common tasks. The activity feed section exists in the UI but data wiring is still partially in development. The realtime.js script updates the stat numbers automatically every 5 seconds without a page reload.

👥 Customer Management — customers.php, customer_ledger.php ▶

Core subscriber CRUD. Each subscriber gets an auto-generated account number like ACC-001. Subscriber names are stored in LASTNAME, FIRSTNAME format. Every subscriber is linked to an Area and a Package. Admin can add, edit, disconnect, reconnect, and confirm installation completion.

active — being billed pending_installation — new, not yet active hold_disconnection — 45+ days overdue, still billed disconnected — no new bills generated reconnected — returns to active billing

The Customer Ledger (customer_ledger.php) displays the complete billing and payment history for a single subscriber, including a Status Change History section showing every disconnect/reconnect event with date, time, and staff name.

💳 Payments — payments.php, print_invoice.php, print_receipt.php ▶

Used by Cashiers and Admins. The cashier searches for a subscriber using a live autocomplete (powered by ajax/search_customers.php), selects a billing period, enters the OR (Official Receipt) number, amount, payment date, and method. The OR number must be unique — it is validated before the record is saved. Based on whether the amount covers the full net_amount, the billing status becomes paid or partial.

Payment Methods: Cash · Check · Online · Others

📄 Billings — billings.php, print_billing_statement.php, bulk_print.php ▶

The billing engine generates one monthly charge record per active subscriber. Admin picks the Month + Year, clicks Generate, and the system creates records for all active and hold_disconnection subscribers. Disconnected and pending_installation subscribers are skipped. A UNIQUE KEY on (customer_id, billing_month, billing_year) prevents duplicate billing.

Additional fees (installation, reconnection, adjustments) are tracked in a separate billing_fees table linked to each billing record. The billing statement print page shows any pending balance from previous months highlighted in red.

🔴 Unpaid Bills — unpaid.php ▶

A quick overview of all outstanding balances, powered by the v_unpaid_subscriptions database view. Can be filtered by Area, Month, and Year. Color-coded rows indicate urgency:

  • 🟢 Green — Less than 30 days overdue
  • 🟡 Yellow — 30 to 60 days overdue
  • 🔴 Red — 60+ days overdue (consider disconnection)

When printing, sidebar and action buttons are hidden for a clean output.

Billing Logic — How Bills Are Calculated

When Admin generates billing for a given month, the engine runs through every active subscriber. Here's exactly how each bill is computed:

BILL CALCULATION FORMULA
internet_fee = subscriber's monthly package fee (can be overridden per customer)
+ cable_fee = optional cable TV charge (default 0)
+ service_fee = repair / call-out fee (default 0)
+ material_fee = hardware/materials charge (default 0)
+ previous_balance = SUM of all unpaid net_amount values from prior months (auto-carried)
= total_amount = sum of all the above
− discount = any applied discount (default 0)
net_amount = total_amount − discount  ←  This is what the subscriber owes
ℹ️

Previous Balance Carryover: If a subscriber has unpaid bills from any prior months, the total of those unpaid net_amount values is automatically added to this month's bill as previous_balance. This means a subscriber's bill grows each month they don't pay. The billing statement print page shows this as a red-highlighted "Total Pending Balance" box.

✅

Duplicate Prevention: The billings table has a UNIQUE KEY on (customer_id, billing_month, billing_year). Running Generate twice for the same month will not create duplicate records — the second run simply skips existing entries.

Real-Time Sync — How It Works

The system doesn't use WebSockets. Instead, it uses AJAX polling — the browser quietly checks for changes every 5 seconds in the background.

Filejs/realtime.js & ajax/check_updates.php
Poll IntervalEvery 5 seconds (5000ms)
Endpointajax/check_updates.php — returns JSON snapshot of key DB counts
Change DetectionCompares new snapshot to stored lastSnapshot — detects any difference in counts or latest activity timestamp
DashboardUpdates stat card numbers in-place without reloading the page
Other PagesTriggers location.reload() for payments, billings, unpaid, reports pages
Tab VisibilityPolling pauses when the browser tab is hidden; resumes when visible (saves resources)
Auth GuardIf session is not set, endpoint returns {error: 'unauthorized'} and polling stops gracefully
Excluded PagesDoes NOT run on login.php or any print_ pages

The JSON response from check_updates.php looks like this:

{
  "ts": "2026-03-20 08:00:00", // latest activity_logs timestamp
  "total_customers": 145,
  "active_customers": 138,
  "total_unpaid": 23,
  "total_payments": 890,
  "total_billings": 1540,
  "disconnected": 5,
  "monthly_revenue": 87450.00
}

If any of these values change between polls, onDataChanged() fires and the appropriate refresh action runs for the current page.

How to Set Up & Run the System

The system runs on XAMPP locally. No internet connection needed once set up.

Install XAMPP

Download and install XAMPP from apachefriends.org. It includes Apache (web server), MySQL (database), and PHP — everything the system needs.

Place the project folder

Copy the billing_system/ folder to: C:\xampp\htdocs\billing_system\

Start Apache and MySQL

Open XAMPP Control Panel. Click Start next to Apache and MySQL. Both should show green status.

Create the database

Open your browser and go to http://localhost/phpmyadmin. Create a new database named exactly: ar_novalink_billing

Import database.sql

In phpMyAdmin, select the ar_novalink_billing database, click Import, and upload database.sql. This creates all tables, views, and default seed data including the 3 default user accounts.

Import the v2.0 upgrade

Also import database_upgrade_v3.sql — this adds the v2.0 tables: package_materials, installation_sketches, customer_status_log, system_settings, billing_fees, and the two database views.

Open the system

Go to http://localhost/billing_system/ in your browser. Log in with admin / admin123. Change all default passwords immediately.

⚠️

Production deployment note: Update DB_PASS in config.php for production. Enable HTTPS and set session.cookie_secure = 1. The system currently has no CSRF protection — add tokens for production use.

SWOT Analysis

An honest evaluation of the system from a technical and business perspective.

💪 STRENGTHS
  • Fully self-contained — runs offline on XAMPP, no internet dependency
  • Role-based access control tightly restricts what each user can do
  • Automatic previous balance carryover prevents billing errors
  • Duplicate billing prevention via UNIQUE KEY constraint
  • Complete audit trail — every action logged with user + IP + timestamp
  • Real-time dashboard updates without full page reloads
  • Print-ready templates for billing statements, receipts, invoices, and installation forms
  • Password security using bcrypt (password_hash)
  • Bulk print functionality for field collection runs by area
  • Customer status lifecycle is well-defined and enforced
⚠️ WEAKNESSES
  • No CSRF protection on any form — vulnerable to cross-site request forgery
  • HTTPS not enforced — data transmitted in plaintext on HTTP
  • Monthly billing must be manually triggered — no automation
  • Non-admin users cannot reset their own passwords
  • Single-server architecture — no failover or redundancy
  • Designed for one company only — no multi-branch support
🚀 OPPORTUNITIES
  • Add GCash / PayMaya payment gateway for online collections
  • SMS billing reminders via Semaphore or Vonage API (affordable in PH)
  • Customer self-service portal reduces office foot traffic
  • Cron job auto-billing reduces monthly admin workload to zero
  • Chart.js dashboard charts for revenue trends and customer growth
  • CSV/Excel export allows external accounting tool integration
  • Mobile-responsive field technician view for on-site installations
  • RESTful API layer could open integration with 3rd-party ISP tools
  • Multi-branch support to scale across more offices or franchises
  • Cloud migration (e.g. shared hosting) for remote access
🔴 THREATS
  • CSRF vulnerability could allow unauthorized payment or account changes
  • No HTTPS means credentials can be intercepted on the local network
  • Default passwords (admin123) pose risk if not changed after setup
  • No database backup utility — hardware failure = data loss
  • Single point of failure — if XAMPP host goes down, system is inaccessible
  • No rate limiting on login — brute-force attacks are possible
  • Dependent on local machine uptime — power outage stops operations
  • Rapid subscriber growth could strain unoptimized queries

Glossary of Terms

Key terms used throughout the system — in the code, database, and documentation.

OR Number Official Receipt
A unique reference number assigned to every payment transaction. Provided by the cashier at time of payment. Must be globally unique across all payments in the system. Used for tracking and audit purposes.
Account Number e.g. ACC-001
Auto-generated unique identifier for each subscriber. Format is ACC- followed by a zero-padded number. Used to quickly look up a customer instead of searching by name.
Previous Balance
The total sum of all unpaid net_amount values from prior billing months for a subscriber. Automatically carried forward and added to the current month's bill during billing generation.
Net Amount
The final amount a subscriber owes for a billing period. Calculated as total_amount minus any discount. This is what appears on the billing statement as "Amount Due."
Billing Generation
The manual process of creating one billing record per active subscriber for a selected month and year. Triggered by Admin from the Billings page. Skips disconnected subscribers and skips duplicates via a UNIQUE KEY constraint.
Hold Disconnection Status
A subscriber status assigned when overdue by 45+ days. The subscriber is still included in billing generation (bills continue to accumulate) but is flagged as a disconnection risk. Shows in yellow on the Unpaid Bills report.
Prepared Statement
A PHP/MySQL technique ($conn->prepare()) where SQL queries are pre-compiled with placeholders (?), and user input is bound separately. This prevents SQL injection attacks by ensuring user data is never interpreted as SQL code.
AJAX Polling
A technique where the browser silently sends a request to the server at regular intervals (every 5 seconds) to check for new data, without the user needing to refresh the page. Used by realtime.js to keep the dashboard current.
Session
A PHP mechanism that stores user data (user_id, role, full_name) on the server temporarily after login. Every protected page checks the session to confirm the user is authenticated before showing any content.
Bcrypt password_hash()
A one-way password hashing algorithm used to store passwords securely. Even if the database is stolen, bcrypt hashes cannot be reversed to obtain the original password. PHP's password_hash() uses bcrypt by default.
Area / Barangay
A service coverage zone used to group subscribers geographically. Every subscriber is assigned to one area. Areas are used for filtering reports, bulk printing billing statements, and field collection routing.
Package
An internet subscription plan with a defined bandwidth (Mbps) and monthly fee. Each subscriber is linked to a package. A subscriber's monthly billing fee defaults to the package fee but can be individually overridden.
Customer Ledger
A per-subscriber financial history page showing all billing records, payment history, total balance, and the status change log (disconnections, reconnections, installations) in chronological order.
Database View SQL VIEW
A saved SQL query that behaves like a virtual table. The system uses v_unpaid_subscriptions (all overdue bills with days overdue calculated) and v_payment_summary (payment statistics per customer). Views simplify complex queries into one reusable object.
Activity Log
An audit trail stored in the activity_logs table. Every significant action (login, payment recorded, customer added, status changed) is automatically written here with the user ID, action type, affected record, description, and IP address.
CSRF Security Term
Cross-Site Request Forgery — a type of attack where a malicious website tricks a logged-in user's browser into performing unwanted actions on the billing system. Currently not protected against in this system.
LCP / NAP / Port Number Network Terms
Network infrastructure identifiers stored per subscriber in v2.0. LCP = Local Convergence Point (fiber distribution point). NAP = Network Access Point (where fiber reaches the subscriber). Port = the specific port on the OLT/switch used for the subscriber's connection.
utf8mb4
A MySQL character set that supports the full Unicode standard including emoji and Filipino characters. The system uses utf8mb4_unicode_ci as the database collation to ensure all characters are stored and compared correctly.

Likely Panel Questions & Answers

Common questions a technical panel or reviewer may ask about this system — with clear, confident answers.

❓ Why did you choose PHP and MySQL instead of a modern framework like Laravel or a JavaScript framework?
A: The system is designed for deployment on a local XAMPP environment in a small ISP setting where the operator may not have access to a terminal, Node.js, or Composer. Vanilla PHP with procedural style requires zero build steps — just copy the folder and import the SQL file. This keeps the deployment barrier as low as possible for a non-technical office environment while still producing a fully functional, secure system.
❓ How does the system prevent duplicate billing for the same subscriber in the same month?
A: The database has a UNIQUE KEY constraint on the combination of (customer_id, billing_month, billing_year) in the billings table. Even if the Admin clicks Generate multiple times, the database will reject any insert that would create a duplicate. The application also checks before inserting and reports a skip count rather than throwing an error to the user.
❓ How is real-time updating implemented? Does the system use WebSockets?
A: No WebSockets are used. The system uses AJAX polling via realtime.js. Every 5 seconds, the browser silently fetches ajax/check_updates.php, which returns a small JSON snapshot of key database counts and the latest activity timestamp. The JavaScript compares this to the previous snapshot. If anything changed, it either updates the dashboard stat cards in-place (no reload) or triggers a full page reload for data-heavy pages like payments or billings. Polling is paused when the browser tab is hidden to save resources.
❓ How does the system handle a subscriber who hasn't paid for multiple months?
A: The billing engine automatically queries the sum of all unpaid net_amount values from prior months and stores that as previous_balance in the new billing record. This means the overdue amount is always carried forward and added to the current bill. The Unpaid Bills page also color-codes urgency — green under 30 days, yellow 30–60, red 60+. The Admin can then manually set the subscriber to hold_disconnection at 45 days or disconnected at 60 days.
❓ What security measures are in place to protect sensitive subscriber and payment data?
A: Passwords are stored using bcrypt via PHP's password_hash(). All database queries use prepared statements to prevent SQL injection. Output is escaped with htmlspecialchars() to prevent XSS. Sessions use HttpOnly cookies. Role-based access control restricts every page via check_permission(). All actions are logged to the activity_logs table with the user ID and IP address. The known gaps are: CSRF tokens are not yet implemented, and HTTPS is not enforced — both should be addressed before production deployment.
❓ What is the purpose of the activity_logs table? Can users view it?
A: The activity_logs table serves as a complete audit trail — every login, payment, customer edit, status change, and report generation is recorded with the acting user's ID, the affected table and record, a human-readable description, and the IP address. However, as of v2.0, there is no UI page to view or filter the log. The data is being captured but can only currently be accessed directly via phpMyAdmin or a database client. An audit log viewer page is a high-priority item on the roadmap.
❓ How does the role-based access control work technically?
A: Every protected page starts with a call to check_permission($required_role) defined in config.php. This function checks if a valid session exists and whether the user's role meets the requirement. If not, it redirects immediately — the page content never renders. The sidebar in includes/sidebar.php also conditionally shows navigation links based on $_SESSION['role'], so users never even see links to pages they can't access.
❓ What happens to a subscriber's billing when they are disconnected and later reconnected?
A: When a subscriber is set to disconnected, they are excluded from future billing generation — no new billing records are created for them. Their existing unpaid balances remain in the database. When the Admin reconnects them (status → active), billing resumes from the next time the Admin runs the monthly Generate process. The reconnection event is logged in the customer_status_log table with date, time, and the staff member who performed the action, visible in the Customer Ledger.
❓ How would you scale or improve this system if subscriber numbers grew significantly?
A: Several improvements would be needed at scale: (1) Add database indexes on frequently queried columns like billing_month, billing_year, and status. (2) Migrate from local XAMPP to a managed server or cloud hosting for uptime and remote access. (3) Implement a cron-based auto-billing scheduler to eliminate manual monthly triggers. (4) Introduce pagination and lazy loading on large list pages. (5) Add a Redis or file-based cache for the dashboard stat queries so they don't hit the database on every poll.
❓ Why is the billing due date set to the last day of the month?
A: The system sets due_date to the last calendar day of the billing month, with a 7-day grace period understood by the staff in practice. This design means billing for March is due by March 31. It aligns with a common ISP billing cycle where the bill covers the current month's service and is due before the month ends. The system uses PHP's date('Y-m-t') to dynamically compute the last day regardless of whether the month has 28, 30, or 31 days.
❓ What is the difference between database.sql and database_upgrade_v3.sql?
A: database.sql is the original v1.0 schema — it creates the core tables (users, customers, billings, payments, areas, packages, activity_logs) and seeds default data including the three default user accounts. database_upgrade_v3.sql is a migration script that adds the v2.0 feature tables without dropping existing data: package_materials, installation_sketches, customer_status_log, system_settings, billing_fees, and the two database views. Both must be imported in sequence for the full v2.0 system to work correctly.
